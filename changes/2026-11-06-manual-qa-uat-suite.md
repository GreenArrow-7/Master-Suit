# A manual QA and UAT suite a tester can run without asking a developer

## What

A role-based manual functional and UAT test suite in `docs/qa/`: twelve numbered
sections, 130 test cases with full steps and expected results, a 65-item smoke
checklist, a 104-row regression list, a 45-item production acceptance checklist
signed by the owner, and an Excel matrix with one row per case and the execution
and defect-tracking columns a tester fills in.

Written from the repository at `1b8226f9069907b6da84e1f868837a2ba9e067e3`
(branch `claude/ponytail-lite-9d4d9a`) on 6 November 2026. No PR yet.

## Why

Asked for by the owner: detailed test cases for every implemented feature,
organised by user role, with exact step-by-step instructions through the UI, so
that a manual tester with no prior knowledge of YOUHAN ONE can sign in, follow
the steps, and record Pass, Fail or Blocked without needing a developer.

The brief was explicit that the cases must come from the implementation rather
than from assumptions or older documents, that UI details which cannot be
verified from the code must be marked rather than guessed, and that nothing may
be marked passed unless it was actually executed.

## Behaviour

No application code, configuration, permission or database record was changed.
This is documentation only.

## Verified

- Every navigation path, label, field, limit, status code and refusal message in
  the suite was read off the code at that commit. The navigation tables were
  produced by running `buildNavigation` against the real model for five
  entitlement combinations; the role matrix by importing the seed's own `ROLES`.
- Where a UI detail could not be established from the code it is marked **Needs
  UI Verification** rather than guessed: the booking-creation screen, the
  Lead Eagle starter roles, the mobile apps, and a handful of exact button
  labels.
- The Excel matrix is generated and checked: 130 rows, 27 columns, every case
  carrying steps and an expected result, no duplicate IDs.
- **Nothing in the suite has been executed.** Every status is `Not Run` and
  every Actual Result is blank, which §12.1 states as the first thing a reader
  sees.

## Left open

Eleven findings from the inspection, each written as a question with the case
that settles it (`docs/qa/12-coverage-and-gaps.md` §12.4). The three worth the
owner's attention first:

- **F-06** — `it_admin` holds `imports:IMPORT` and `exports:EXPORT` and no
  `leads` grant. Whether that is enough to export the lead book could not be
  determined by reading. If it is, the role boundary is cosmetic. `TEN-FIELD-005`
  step 8 settles it in two requests.
- **F-07** — `it_admin` and `hr_admin` hold `roles:ASSIGN` at ORGANIZATION.
  Whether either can assign itself `org_admin` could not be determined by
  reading. `ADMIN-ROLE-004` steps 6–8 settles it.
- **F-03** — `POST /api/v1/bookings` and the payout routes assert
  `productModule: 'SALES'`, while collections, commissions, events and proposals
  around them accept `SALES_OR_REALTY`. So a Real-Estate-only brokerage sees the
  Deals area and cannot create a booking or release a payout.

Also open: no seeded plan or workspace is entitled to `LEAD_EAGLE` (F-01); there
is no Lead-Eagle-specific role, so the brief's "configurable starter roles" are
the shared roles inside a Lead-Eagle-only workspace (F-02); `allocation` is
granted to no role below administrator (F-05); `limits.publicForm` and
`limits.publicShare` are declared and unused (F-08); and the mobile apps'
status is contradictory between a code comment and `PROJECT.md` (F-10).

Not covered, and why, in §12.5: performance and load, accessibility, the browser
and device matrix, the mobile apps, email rendering, the conversations inbox,
service tickets and SLA, automation rules, contests and the engagement feed, and
calendar sync.

`PROJECT.md` is unchanged: nothing here makes it wrong.
