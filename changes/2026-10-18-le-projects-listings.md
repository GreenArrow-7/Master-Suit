# Projects and listings for every lead module: payment plans, uploads, units from the page, paging and views, permits, pocket listings, unit matches

**18 Oct 2026** · PR #207 · feature · Lead Eagle, projects, listings (audit rows M11-01, M11-02, M11-03, M11-04, M11-07, M11-08, M11-09, M12-02, M12-04, M12-05, M12-06, M12-09)

**What.**

- **Payment plans (M11-02).** `PaymentPlan` (name, milestones `[{ label, percent }]` summing to 100). `GET/POST/DELETE /api/v1/projects/{id}/payment-plans` (LEAD_MODULES; EDIT to write). The project page lists them and adds one ("20 On booking, 80 Post-handover"; once semicolons separate, a label keeps its comma: "40 Post-handover, 4 years"). A stage with nothing due (0%) is a milestone. The move tool carries the standalone's plans; one whose milestones cannot be read is reported, not silently emptied.
- **Uploads (M11-03, M12-02).** `POST /api/v1/projects/{id}/media/upload` and `/listings/{id}/media/upload`: multipart, recognised by bytes (photo: JPEG/PNG/WebP; floor plan, brochure, creative: also PDF), malware-scanned, stored under `inventory/t-{tenant}/`, served by the existing `media/{mediaId}/file`. "Add photo or file" on both pages. A listing outside an OWN agent's reach answers 404, on the upload and on the JSON listing-media POST and DELETE alike. The JSON media routes now link a video or tour and nothing else: they take no `storageKey`, `mimeType` or `sizeBytes`, so a hosted file's row and type come only from the upload (before, a registered key could point at any object in the bucket, and a caller-named type let an uploaded PDF be re-registered as `text/html` and served as a page on our origin). The file routes render only a type the upload recognises (`mediaFileHeaders`); any other stored type is served as `application/octet-stream`, `attachment`.
- **Developer, community, amenities by name (M11-01).** The project form (and the listing form, for the community) takes them typed; each is found (case and spacing aside: "emaar" is the Emaar on file) or created, so the catalogue's filters work in a wizard-made workspace. The catalogue gains an Amenity filter.
- **Units from the project page (M11-04).** Add unit plan and Add units (floor range) call the existing routes, which now take the form's numbers as typed; the counts and the unit board follow.
- **Catalogue and book (M11-08, M12-05).** Both page past 50 rows (Pager). The catalogue's filters show their counts (`catalogueFacets`, shared with `/projects/facets`). Each person saves views of either list (`/api/v1/projects/views`, `/listings/views`; `SmartView` objectType `PROJECT_LIST`/`LISTING_LIST`). Listings filter by beds up to and price from. Opening a saved view or clearing the filters refills the typed inputs (each is keyed on its own value), so leaving one no longer undoes the view.
- **Listing status and permit (M12-04, M12-09).** The listing page sets its status (Active needs a live mandate, as the API already said) and its Trakheesi permit and expiry (expired only after its last day in the workspace's time zone); the new-listing form takes them too. Administration → Company stores the ORN. An Active listing never sent to a portal is a pocket listing: it matches and shares.
- **Unit matches on the lead page (M12-06).** Matching stock lists AVAILABLE units of projects the requirement fits (community, beds, area, budget, handover) beside the listings. The lead page's requirement composer saves its typed Areas as before and, for each that names a community on file (case aside), its `micromarketIds`, so units and listings narrow by community from the page.
- **Lead grid by project (M11-07).** Filters → "Interested in" picks a project; the chip names it. (The link, its picker, the project page's interested leads and the move were #172.)
- **Move tool (M11-09).** A unit keeps its type and bedrooms on a unit plan per (project, type, bedrooms); payment plans move; a moved project's unit counters and types are counted (they were 0), its price band kept (`recalculateProjectRollups(..., { countsOnly: true })`); media stays behind, reported.

One migration (`20261018100000_project_payment_plans`, additive: one table under forced row-level security).

**Decisions taken.**

- Media is not moved: its files are in the standalone's bucket; the report counts the rows left.
- Unit matches do not filter on property type (a plan's type is free text) and carry no score: `demand.ts` keeps its rule against invented weights.
- A typed community with no city is Dubai, the standalone's default.
- BOOKED stays off the unit board: booking names the buyer and belongs to Bookings (Real Estate); a Lead-Eagle-only workspace holds units.
- Paging is OFFSET (marked `ponytail:`); a keyset like the lead grid's when a catalogue passes ~10,000 rows.
- The JSON media routes refuse `storageKey` outright rather than check a caller's type against a list: no screen used it, an upload already makes its own row, and a second row on one object only re-opened the type question. The file routes do not add `Content-Security-Policy: sandbox`: it stops Chrome's PDF viewer, which is how a brochure previews; only images and PDFs (types that run no script) render inline.
- A typed area names a community only when one with that name is on file; the composer never creates one. The composer's body is the whole requirement, so its save replaces `micromarketIds` (a set written through the Requirements API is recomputed from the areas). The composer still has no area (sq ft) field; budget, beds and location are the acceptance.
- A developer or community typed in another case keeps the spelling first recorded.
- In the one-line milestone field, a semicolon or line break separates once present; otherwise commas do. A comma followed by a number cannot tell a new milestone from "Post-handover, 2 years", so no lookahead rule was used.
