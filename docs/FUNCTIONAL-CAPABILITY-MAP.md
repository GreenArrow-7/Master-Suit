# Functional capability map

What each integration and cross-cutting capability actually does, graded by
reading the code rather than by trusting configuration or older documents.

**How to read a grade.** `WORKING` means the whole chain exists and something
executed it. `NOT VERIFIED` means the code is there and correct as far as
reading can establish, but the external half could not be exercised here — it is
never a synonym for "probably fine". A row is graded down for the weakest link
in it, so an integration with a perfect adapter and no operational log is
`PARTIAL`.

**Scope, stated honestly.** This covers the integration surface and the areas
audited in depth during this work. It is not yet a map of all ~65 customer
screens; the sections at the end name what has not been audited so nobody reads
an absent row as a clean one.

Evidence is a file path. Where a claim rests on a test, the spec is named.

## What could not be exercised here, and why

Every `NOT VERIFIED` row above is one of two things, and they are not the same
claim. Both were established by trying, not by assuming.

**Reachable, and refused for want of a credential.** The vendor answered. Only
the key is missing.

| Endpoint the code calls                                    | Unauthenticated response                                              |
| ---------------------------------------------------------- | --------------------------------------------------------------------- |
| `generativelanguage.googleapis.com/v1beta/models` (Gemini) | `403 PERMISSION_DENIED` — "Method doesn't allow unregistered callers" |
| `speech.googleapis.com/v1/speech:recognize` (Google STT)   | `403 PERMISSION_DENIED` — same                                        |
| `www.googleapis.com/calendar/v3/calendars/primary`         | `401` — "Request is missing required authentication credential"       |

**Not reachable at all.** This environment's egress policy answers `403` to the
CONNECT, so no credential would help here even if one existed:
`graph.facebook.com`, `www.facebook.com`, `api.twilio.com`, `api.plivo.com`,
`kpi.knowlarity.com`, `api.exotel.com`, `api.deepgram.com`, `openrouter.ai`.
Outbound SMTP on 587 times out and there is no local MTA, which is the same
answer for the mailer.

There are also no credentials to try. `META_APP_ID`, `META_APP_SECRET`,
`GEMINI_API_KEY`, `SMTP_HOST`, `SMTP_USER` and `SMTP_PASSWORD` are empty,
`EMAIL_PROVIDER` and `WHATSAPP_PROVIDER` are `mock`, and `IntegrationConnection`
holds **zero rows** across both tenants — so no workspace had connected a
provider out of band either.

What that leaves verified for those integrations is everything on this side of
the wire, which is not nothing: 58 tests across the Meta and WhatsApp surface
(webhook signature, subscription handshake, deduplication, normalisation,
template sync, reply capability) and 92 across telephony, integration
connections, AI provider selection and redaction — executed, passing. Exactly
one thing in each row is unverified: the live exchange with the vendor.

**The face engine was in this list and should not have been.** It is a sidecar
in this repository, not a third-party service, so "no credentials" was never the
reason — it needed installing, which is a different sentence and a much weaker
one. It now has a row of its own above, with measured numbers.

## Open gaps, in the order they are worth closing

1. **Outbound integration event log** (§33) — inbound is recorded on
   `WebhookEvent`; outbound provider calls are logged and not queryable, and
   there is no error category or direction on either.
2. **External billing** — fields exist, integration does not. Waiting on a
   payment provider being chosen; that is a commercial decision, not a coding
   one, and picking one by default would be the wrong kind of initiative.
