## Packet C — `EVC-005`, backup and restore. Still blocking, with a named cause.

**Backups are running.** `master-suite-backup.timer` and
`master-suite-backup-status.timer` are enabled and firing; the most recent
manifest is `/var/backups/master-suite/20260909T074609Z/manifest.txt`, carrying
`pg_version`, per-table row counts for reconciliation, and sha256 sums for
`database.dump`, `database.dump.gpg` and `objects.tar.gpg`.

**Restore has never once succeeded**, which is what `EVC-005` actually asks
for. `master-suite-restore-verify.service` fails every run. Two distinct causes
from the journal, neither guessed:

1. `[verify] no manifest.txt in /var/backups/master-suite/latest` — the
   `latest` pointer the script depends on is absent, so the local path fails
   before it starts.
2. `NOTICE: Config file "/root/.config/rclone/rclone.conf" not found - using
   defaults`, then the off-host verification aborts — `rclone` has no
   configuration, so `rclone:hetzner:youhan-one-prod-backups/master-suite`
   resolves to nothing. `BACKUP_REMOTE` was also reported unset on the
   2026-09-06 04:16 run.

**Required, by a human:** configure `rclone` for the Hetzner remote, set
`BACKUP_REMOTE`, establish the `latest` pointer contract, then run
`restore-verify.sh` **against an isolated scratch target** and reconcile the
row counts in the manifest against the restored database.

`EVC-005` cannot move to PASS until an actual restore succeeds. Nothing in this
incident's work changes that, and no restore was attempted — the script tears
down a scratch database and bucket, which is destructive enough to need the
owner.

## Packet D — production monitoring is down. Two days. R5.

**Evidence, read-only:**

```
infra-prometheus-1     Restarting (1)   RestartCount 171+
infra-alertmanager-1   Restarting (1)

prometheus:    /etc/prometheus/entrypoint.sh: line 46:
               can't create /run/prom/metrics-token: Permission denied
alertmanager:  /etc/alertmanager/entrypoint.sh: line 88 and 109:
               can't create /run/am/alertmanager.yml: Permission denied
```

First occurrence **2026-09-07 08:42:46Z**; 1112 occurrences since. Both
containers run as `nobody` (`Config.User = nobody`) and both entrypoints render
their config into a `tmpfs` — `{"/run/prom":""}` and `{"/run/am":""}` — mounted
with default ownership, which is `root`. Prometheus started cleanly on
2026-09-04, so this began later, not at first deployment.

**Consequence:** no metrics scraping and no alerting on the production host
since 2026-09-07. The twelve alert rules `check:observability` counts are
loaded nowhere.

**Not fixed here, and not to be fixed with a live `chmod`.** `infra/*` is `R5`
in `docs/RISK_CLASSIFICATION.md`: human execution only. The remediation belongs
in `infra/docker-compose.yml` where the two `tmpfs` entries are declared —
giving the mounts the container's uid (`tmpfs: ['/run/prom:uid=65534,gid=65534']`
or equivalent), or running the entrypoint as a user that can write them. It
needs the change, a rebuild of that service, and then:

- `docker ps` shows both healthy and `RestartCount` stable,
- Prometheus targets scrape,
- the alert rules load,
- `/api/metrics` answers for the token-gated scraper,
- a test alert traverses the path, where that is safe to trigger.

**No release should be called production-ready while alerting is off.**
