## Packet C — `EVC-005`. **RESTORE VERIFIED 2026-09-09. Two defects fixed.**

### The reason it had never once succeeded

Not configuration. A regex.

```sh
EXPECTED_SHA="$(grep -E '  ?\./?database\.dump$' "${SRC}/manifest.txt" | ...)"
```

`\./?` makes only the **slash** optional; the dot is mandatory. `backup.sh`
writes the plain artefact with `sha256sum database.dump` — no `./` — and
appends the encrypted ones later with `sha256sum ./*.gpg`, which do carry it.
So the pattern matched nothing, the capture came back empty, and because
`set -e` fails an assignment whose command substitution exits non-zero, the
script **aborted at that line on every backup ever taken — before restoring
anything.**

It reads as "decrypting …" then straight to teardown, which is exactly what the
2026-09-06 journal showed and why it looked like a decryption or credential
problem. It was neither.

`(\./)?` is the fix, plus `|| true` so a manifest genuinely missing the line
degrades to the "no sha recorded" branch instead of killing the run.

The earlier readings were both wrong, and are corrected here: `latest` exists
and is a correct symlink; `rclone` is fully configured through
`RCLONE_CONFIG_HETZNER_*` in `/etc/master-suite/backup.env`, which is why the
`rclone.conf not found` line is a `NOTICE` and not the failure. The off-host
pull works and takes ~47 s.

### Second defect, exposed by the first being fixed

`backup-status.sh` line 94 fed `find -printf '%T@'` — a float — into shell
arithmetic. It could never have run before, because it only executes when a
`.verified-at` marker exists and no verification had ever produced one. The
first successful verify created the first marker and the daily freshness check
began erroring immediately. Fixed by truncating the fraction.

### Evidence — an actual isolated restore

Run against `20260909T074609Z`, into the scratch database
`leadflow_restorecheck`, which the script drops before and after. Production's
database and bucket are never touched.

```

[verify] verifying the off-host copy at /tmp/…
[verify] ok    dump checksum matches the manifest
[verify] ok    dump restored without errors
[verify] ok    migration ledger is clean and at head (65/65)
[verify] ok    Tenant: 1
[verify] ok    object count: 0
[verify] ok    every ingested recording has its object in the backup
[verify] RESTORE VERIFIED (off-host copy)
```

Confirmed three ways: directly against the pulled copy, via `--prefer-remote`,
and through `systemctl start master-suite-restore-verify.service` —

The off-host copy was independently checked byte-for-byte against the local

## Packet D — production monitoring. **RESTORED 2026-09-09 16:12 UTC.**

### What was wrong

`infra-prometheus-1` and `infra-alertmanager-1` crash-looped from **2026-09-07
08:42:36** to 2026-09-09 16:12, 1112 logged failures:

```
prometheus:    can't create /run/prom/metrics-token: Permission denied
alertmanager:  can't create /run/am/alertmanager.yml: Permission denied
```

### Trigger, established from the journal

`2026-09-07 08:42:36` is the **host booting into kernel 6.8.0-139** (it had been
running 6.8.0-138). Both containers were **created on 2026-09-04**, under the
previous kernel. After that reboot their `tmpfs` mounts were no longer applied
as they had been, so `/run/prom` and `/run/am` were not writable by the `nobody`
(65534) user the images run as, and both entrypoints died on their first write.

They are the **only two services in the stack that use `tmpfs`**, which is why
nothing else was affected even though every other container is the same age.

Nothing brings the stack up at boot: there is no compose systemd unit, only
Docker's own `restart: unless-stopped`, which **restarts containers but never
recreates them**. A restarted container keeps its original mount setup. That is
the whole mechanism.

### What was done

`docker compose … up -d --force-recreate prometheus alertmanager`, with
`IMAGE_TAG` and all four overlay files, touching those two services only. No
application service was restarted, no image changed, no data touched.

### Verified after

| Check | Result |
|---|---|
| Prometheus | `Up (healthy)`, **RestartCount 0** |
| Alertmanager | `Up (healthy)`, **RestartCount 0** |
| Active targets | 2 of 2 `up`, no scrape errors (`master-suite`, `prometheus`) |
| Alert rules | 7 groups, **12 rules, all health `ok`** — matching `check:observability` |
| Ingestion | `up{job="master-suite"} = 1`, `up{job="prometheus"} = 1` |
| Alertmanager | cluster `ready`, 5 receivers configured |

### What was NOT established, stated plainly

The precise mechanism inside the stale container. The obvious reading of the log
— that the `tmpfs` was mounted root-owned and unwritable — was **tested and
disproved**: a container from the same image, same entrypoint, same
`tmpfs: ['/run/prom']`, same `nobody` user starts cleanly and the mount is mode
`1777`. Recreating the container fixed it, and doing so destroyed the evidence.

**No compose change has therefore been committed.** Writing an ownership fix for
a cause that was disproved would be guessing, and it would read as diagnosed.

### What still needs an owner's decision

1. **Nothing recreates containers after a host reboot.** `restart:
   unless-stopped` is not enough for a service whose correctness depends on a
   mount being reapplied. Either a boot-time `docker compose up -d` unit, or a
   documented post-reboot step. A new systemd unit changes the boot behaviour of
   the whole stack, which is outside the monitoring-only authorization given,
   so it is raised here rather than implemented.
2. **Monitoring cannot report its own outage.** Prometheus cannot alert that
   Prometheus is down, and an Alertmanager that is down delivers nothing. This
   outage ran for two days and was found by a person reading `docker ps`, not by
   an alert. A dead-man's-switch — an always-firing alert whose *absence*
   downstream is the signal — is the standard answer and does not exist here.

**Interim runbook, until (1) is decided:** after any reboot of this host, run
`docker compose … up -d` (all four overlays, `IMAGE_TAG` set) rather than
relying on the restart policy, then confirm `RestartCount 0` on both monitoring
containers.

## Packet F — post-reboot durability. **IMPLEMENTED and lifecycle-tested.**

### The recurrence risk, precisely

Nothing brings this stack up at boot. Docker's `restart: unless-stopped` does,
and it **restarts** containers — it never **recreates** them. A restarted
container keeps the mount setup it was created with, which is why the
2026-09-07 kernel change broke the only two services that depend on a `tmpfs`
being reapplied.

### What was implemented

`scripts/recreate-runtime-services.sh` + `infra/systemd/master-suite-recreate-runtime.service`,
a `oneshot` unit ordered `After=docker.service network-online.target`.

**Scoped to `prometheus` and `alertmanager` only, and that is deliberate.**
`docker-compose.prod.yml` resolves the application images as
`${IMAGE_TAG:-dev}`. A whole-stack `up -d` at boot with `IMAGE_TAG` unset would
silently recreate web and worker from `master-suite/web:dev` — a stale image
that has already caused one outage on this host. Naming exactly the two
services that need recreating means the application containers cannot be
touched by the fallback.

`IMAGE_TAG` is still resolved, because Compose interpolates the whole file
before selecting services. It is read from a **running container**, never
defaulted, and the script **fails closed** if it cannot be determined or
resolves to `dev`.

### Explicitly not done

No root containers. No world-writable directories. No cron loop. No blind
periodic restarts. It runs once, after Docker, and is a no-op when nothing
needs recreating.

### Lifecycle test — passed, without rebooting

```
systemctl start master-suite-recreate-runtime.service   →  Result=success, status=0
  IMAGE_TAG=c879c6c7f7e8; recreating prometheus alertmanager
  infra-prometheus-1   health=healthy  restarts=0   (recreated 18:00:25)
  infra-alertmanager-1 health=healthy  restarts=0   (recreated 18:00:25)
```

| Check | Result |
|---|---|
| Correct tag resolved from a running container | `c879c6c7f7e8`, not `dev` |
| Only the two services recreated | yes — new `Created` on both |
| **Application containers untouched** | `infra-web-1` / `infra-worker-1` still `StartedAt 07:43:18`, same image |
| Targets still scraping afterwards | `up{prometheus}=1`, `up{master-suite}=1` |
| Fail-closed when the tag is unresolvable | exit `1`, Compose never invoked — tested with a shim |
| Enabled at boot | `multi-user.target.wants` symlink created |

**A real reboot has NOT been performed.** Proving the boot path end to end
requires rebooting production, and that needs your explicit approval. Everything
short of the reboot itself is tested.

## Packet G — monitoring self-detection. **DESIGNED, not implemented.**

Prometheus cannot alert that Prometheus is down, and an Alertmanager that is
down delivers nothing. The 2026-09-07 outage ran two days and was found by a
person reading `docker ps`.

Every option needs something **outside this host**, which is why none was
implemented under an authorization scoped to this host:

| Option | What it needs | Notes |
|---|---|---|
| External uptime check on `/api/health` | an external service | simplest; proves the app, not the monitoring |
| Dead-man's switch (Healthchecks.io / Cronitor / equivalent) | an external endpoint + token | the standard answer: an always-firing alert routed out; **absence** is the signal |
| Alertmanager heartbeat receiver on a second host | a second host | no external dependency, but there is no second host |
| Host watchdog posting to an external collector | an external collector | independent of Prometheus entirely |

**Release-impact classification: NOT release-blocking, but it is the control
that would have caught this outage on day one rather than day three.** Recommend
the dead-man's switch as a follow-up with a named owner. It cannot be closed
from inside this host.
