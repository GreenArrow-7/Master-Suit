### The concrete reason the app still fails

**The fixed code has never been on the server the phone loads.**

The app is a thin WebView over `https://one.youhan.in`. Every screen in this
report is rendered by `apps/web` on that server. The fixes were written on
9 November on `claude/ponytail-lite-9d4d9a`; that branch is not merged into
`main`, `main` itself is not deployed, and production still serves `1f98183b`
from 5 November — code that predates every fix here.

So nothing about the iPhone, its build, its cache or its WebView is the cause of
defects 2 to 6. Reinstalling the app would change nothing: it would re-download
the same unfixed pages. This was checked rather than assumed — the alternative
explanation, that the app carries its own stale copy of the interface, is ruled
out by `apps/mobile/www/` containing a single 1100-byte "Not configured"
placeholder and no built assets at all.

### What this means for delivery

**No new iOS build is required for defects 2 through 6.** They are hosted code.
Deploying the web artifact puts the fix on the phone at the next page load, with
nothing for the reporter to install and no App Store or TestFlight step.

A new iOS build would only be needed if the fix were in the native shell or its
plugins. None of it is.

### Two facts that need the owner's attention

1. **The build labelled "staging" was compiled against production.** At the time
   of run 18 the repository variable `IOS_STAGING_URL` was itself set to
   `https://one.youhan.in`; it is now `https://ios-staging.youhan.in`. So the
   TestFlight build in the reporter's hands talks to the live customer database
   while the workflow's own header comment says it "never targets production".
   Any testing done on that build has been testing on production.
2. **The version numbers disagree.** Xcode says 1.2.0; the user agent the server
   sees says `0.1.0-dev-poc`. Support cannot identify a build from the server

### 1 — Blank screen after lead creation/editing · NOT FIXED

Reproduction attempted: signed in at a 375×812 viewport, created a lead from
**Add lead**, then **More ▾ → Edit details**, changed tags, saved. Both journeys
completed; the lead and the tags persisted; the screen stayed usable. Repeated
across sessions. **Not reproduced, so not diagnosed.**

Ruled out, each by inspection rather than assumption:

- not a failed write — the lead and the tags are in the database afterwards;
- not the service worker — `public/sw.js` answers only requests whose mode is
  `navigate`, which is not how a React Server Component payload is fetched, so
  it never sees the refresh;
- not a missing page-level error boundary — `app/error.tsx` exists and would
  render a panel rather than nothing.

Still open, and untested here because each needs the phone:

1. **`router.push()` immediately followed by `router.refresh()`** —
   `LeadForm.tsx:94-95` and ten other places. The refresh can abort a
   navigation that has not settled. On a local connection it never loses the
   race; over a phone's network it can.
2. **A failed RSC fetch.** `patchLead` calls `router.refresh()` after the write.
   What the WebView shows when that fetch fails mid-flight has not been observed.
3. **No `global-error.tsx`.** `app/error.tsx` does not catch an error thrown in
   the root layout, and nothing catches a client navigation that resolves to an
   empty tree. A blank page that survives until the app is killed is consistent
   with that and with nothing else found here.

An error boundary or a forced reload would hide whichever of these it is, so
neither was added.

**The operator test, four steps, on the affected phone:**

1. Open **Safari** on the phone — not the app — to `https://one.youhan.in` and
   repeat the tag edit. Blanks in Safari too → the web application. Only in the
   app → the WebView.
2. With the app blank, pull down to reload. Page returns → the document survived
   and the React tree was lost. Page does not return → the WebView's own page
   failed.
3. Capture the build: **Settings → General → iPhone Storage → YOUHAN ONE**
   shows the version, and TestFlight shows the build number. The server build is
   on the **Administration → Integrations** page of the workspace, bottom of the
   page — _not_ on `/api/health`, which reports only database and Redis.
4. If it reproduces in Safari, open Safari's Web Inspector from a Mac and record
   the **first** console error and the status of the request made at the moment
   of the save.

Those four answers settle it in one sitting.

### 2 — Employee selection returns "0 items" · IMPLEMENTED, NOT DEPLOYED

**Root cause.** The control was `<select multiple>`. iOS renders that as a
single-line control that opens the one-column picker wheel, and that wheel
cannot express more than one choice, so every tap replaced the last and the
field stayed at "0 items" however many names were tapped. No amount of CSS
reaches it: the control is drawn by the system.

**Fix.** A checkbox group in `WorkspaceRecordForm` with 44px touch targets.
`FormData.getAll` already collected repeated names, so the submit path is
unchanged. The component builds the multi-choice field on 19 screens.

**Evidence.** In a browser at 375×812 against a seeded database: two employees
ticked, assigned, both rows present as `ACTIVE`/`PRIMARY` in
`HrEmployeeLocationAssignment`.

### 2b — The same defect on two further screens · IMPLEMENTED, NOT DEPLOYED

Found by asking the question the first fix should have asked: _where else?_
Two screens built their own multi-select rather than using the shared component,
and both were broken on a phone in exactly the same way:

- **Sales → Automatic assignment** — the "People" and "Only leads from these
  sources" pickers (`RulesPanel.tsx`). A rule could never be given more than one
  person on a phone, which silently changes who leads are handed to.
- **Administration → Teams** — the "Members" picker (`TeamsPanel.tsx`). A team
  could never be given more than one member on a phone, and TEAM data scope
  binds to that membership.

Both are now checkbox groups using the same classes. `getAll` was already used
on both submit paths, so neither server contract changed.

**Evidence from the running application**, at 375x812 and driven by mouse: on
Administration -> Teams, two members ticked and the team created comes back
holding both. Each row measures exactly 44px tall and the page does not scroll
sideways. On Sales -> Automatic assignment both groups render, no
`select[multiple]` remains, and an empty source list says so instead of
offering a dead control.

**Evidence.** `tests/unit/no-multiple-select.spec.ts` — new. It walks `src` and
fails on any `<select multiple>`, comments stripped. Confirmed to fail on the old
markup by restoring `TeamsPanel.tsx` and re-running. This is the regression test
for the whole class, not for one screen, because the defect is invisible to
anyone developing on a desktop.

### 3 — Test-like role options · IMPLEMENTED at source, NOT DEPLOYED

**Root cause.** Three Playwright specs clone roles and create accounts **inside
the shared demo workspace**, tagging what they create with their own
`Date.now()` rather than the run marker. `globalTeardown` deletes tenants whose
slug ends with `RUN_TAG`, so that workspace survives every run and its rows
accumulate, one set at a time: "Journey Rep …", "Scope probe …", "Daily
Workflow …".

**Fix.** The three specs tag with `RUN_TAG`; teardown also deletes roles and
work locations carrying it. Matched on the marker, never on "looks like a test".

**Still open, and it is the part that matters.** The fix stops new rows. It does
not remove the rows already there. If the suite has ever been pointed at a
customer workspace, those are grantable roles in a workspace somebody uses — a
role boundary nobody chose. That needs an exact inventory before anything is
deleted, matched on the run marker and never on a name. **Not done**, because it
needs to be run against the environment that holds them and the only way to know
which workspace `E2E_DEMO_SLUG` names is to read that environment's
configuration.

### 4 — Ineligible reporting-manager options · IMPLEMENTED, NOT DEPLOYED

**Root cause.** The query filtered the employee record (`deletedAt`,
`employmentStatus`) and never the login behind it, and `setManager` accepted any
id the form sent. So "Deleted account – DEL-001" was offered and accepted.

This is worse than it looks: a manager who cannot sign in still approves leave
and payslips on paper only. A request routed to a suspended account waits with
nobody able to act on it.

**Fix.** The list requires `membership.status === 'ACTIVE'`; `setManager` and the
HR employee PATCH both refuse a non-active membership, so the rule holds for a
request that never came from the form. Reporting lines already recorded are left
exactly as they are — no historical record was rewritten.

**Evidence.** `tests/hr/manager-eligibility.spec.ts` — 3 cases. Both refusal
cases fail when the new check is removed, which was run to confirm it.

### 5a — Missing department / designation options · IMPLEMENTED, NOT DEPLOYED

**Root cause.** `Designation` had a complete API — list, create, update,
delete — and **no screen anywhere in the application**. No workspace could ever
configure one, so the field on **Add user** could only read "Not set".

**Fix.** Designations sit beside departments on the existing page, which becomes
**Departments & designations**. Where a list is genuinely empty the field says
"None configured yet" with a link to the setup page, instead of a dropdown
holding nothing.

**Evidence.** The focused HR journey creates a department through the UI and
asserts it appears — see section 3.

### 5b — Missing branch options · NOT FIXED

`Branch` rows can be created **only by the seed**. There is no API and no
screen. A real workspace can therefore never populate the field, and never use
BRANCH data scope — which the role system offers. The field now says the branch
can be left unset rather than showing an empty dropdown, but that is honesty,
not a fix. Branch administration is a separate change and needs a decision about
who administers it.

### 6 — Missing sub-source options · IMPLEMENTED, NOT DEPLOYED

The control was correct — disabled because the chosen source has no
sub-sources — but a disabled "—" reads as broken. It now says which it is: "No
sub-sources configured for this source." or "Choose a source first."

### 7 — Lead validation inconsistencies · NOT FIXED, by design

`createLead` requires only `fullName`, and the form marks exactly that field. So
the form and the server agree, and the report is a requirements question rather
than a defect.

It was left alone deliberately. Imported and cold-called leads often have
neither a phone nor an email, so making both mandatory would break import, and
making every field mandatory would break more. **What a lead must carry, and at
which stage, is a business rule that has not been written down.** Once it is, it
is a small change.
