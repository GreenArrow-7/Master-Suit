## D-01 in detail — the blank screen

This is the P0 and it is the one still open, so the detail matters.

**What was tried.** Signed in as `org_admin` at a 375×812 viewport: created a
lead from **Add lead**, which redirected to the lead and rendered it; opened
**More ▾ → Edit details**, set tags to `vip, investor`, saved, and watched the
tags appear on the lead. No blank screen, no console error, no failed request.

**What that rules out.** Not a server error on the write (the lead and the tags
both persisted). Not the service worker: `public/sw.js` only answers requests
whose mode is `navigate`, which is not how a React Server Component payload is
fetched, so it never sees the refresh. Not a missing error boundary at the page
level — `app/error.tsx` exists and would render a panel rather than nothing.

**What it does not rule out.** The native app is a WebView pointed at the live
server (`apps/mobile/capacitor.config.js`), so it runs the same code over a
phone's network against a production build. Three differences from this test
remain untested here:

1. **`router.push()` immediately followed by `router.refresh()`** — the pattern
   in `LeadForm.tsx:94-95` and ten other places. The refresh can abort the
   navigation that has not settled; on a fast local connection it never loses
   the race, on a phone it can.
2. **A failed RSC fetch.** `patchLead` calls `router.refresh()` after the write.
   What the WebView shows when that fetch fails mid-flight was not observed.
3. **No `global-error.tsx`.** `app/error.tsx` does not catch an error thrown in
   the root layout, and nothing catches a client-side navigation that resolves
   to an empty tree. A blank page that survives until the app is killed is
   consistent with that, and with nothing else found here.

**The shortest operator test**, for somebody holding the affected device:

1. On the phone, open Safari (not the app) to the same server and repeat the
   tag edit. If it blanks in Safari too, it is the web application; if only the
   app blanks, it is the WebView.
2. With the app blank, pull down to reload. If the page comes back, the document
   survived and the React tree was lost; if it does not, the WebView's page
   itself failed.
3. Capture the build: Settings → the app's version string, and the `BUILD_COMMIT`
   the server reports at `/api/health`.
4. If reproducible in Safari, open Safari's Web Inspector from a Mac and record
   the **first** console error and the status of the request made at the moment
   of the save.

Those four results would settle D-01 in one sitting. Without them any change is
a guess, and the brief asked for evidence rather than a guess.

## Open questions for the business

1. **D-05a — what must a lead carry?** Today only a name. The reporter expects
   more. Whether a phone or an email should be required, and at which stage,
   is a business rule nobody has written down; imported and cold-called leads
   often have neither, so making both mandatory would break import.
2. **D-04b — who administers branches?** The field exists, the data scope
   BRANCH depends on it, and nothing in the product can create one.
3. **Has the E2E suite ever been pointed at a customer environment?** D-03a says
   it has been pointed at whatever `E2E_DEMO_SLUG` names. If that was ever a
   real workspace, the roles and accounts it left need an inventory before
   anything is deleted — by marker, never by name.
