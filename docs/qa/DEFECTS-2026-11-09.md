### The concrete reason the app still fails

**The fixed code has never been on the server the phone loads.**

The app is a thin WebView over `https://one.youhan.in`. Every screen in this
report is rendered by `apps/web` on that server. The fixes were written on
9 November on `claude/ponytail-lite-9d4d9a`; that branch is not merged into
`main`, `main` itself is not deployed, and production still serves `1f98183b`
from 5 November — code that predates every fix here.

So nothing about the iPhone, its build, its cache or its WebView is the cause of
defects 2 to 6. Reinstalling the app would change nothing: it would re-download
the same unfixed pages. This was checked rather than assumed — the alternative
explanation, that the app carries its own stale copy of the interface, is ruled
out by `apps/mobile/www/` containing a single 1100-byte "Not configured"
placeholder and no built assets at all.

### What this means for delivery

**No new iOS build is required for defects 2 through 6.** They are hosted code.
Deploying the web artifact puts the fix on the phone at the next page load, with
nothing for the reporter to install and no App Store or TestFlight step.

A new iOS build would only be needed if the fix were in the native shell or its
plugins. None of it is.

### Two facts that need the owner's attention

1. **The build labelled "staging" was compiled against production.** At the time
   of run 18 the repository variable `IOS_STAGING_URL` was itself set to
   `https://one.youhan.in`; it is now `https://ios-staging.youhan.in`. So the
   TestFlight build in the reporter's hands talks to the live customer database
   while the workflow's own header comment says it "never targets production".
   Any testing done on that build has been testing on production.
2. **The version numbers disagree.** Xcode says 1.2.0; the user agent the server
   sees says `0.1.0-dev-poc`. Support cannot identify a build from the server
   side today.

### A release prerequisite that will otherwise abort the deploy

`docker-compose.azure.yml` gained a Grafana service in this PR, declared
`GF_SECURITY_ADMIN_PASSWORD: ${GRAFANA_ADMIN_PASSWORD:?set GRAFANA_ADMIN_PASSWORD in apps/web/.env.production}`.

Compose interpolates the whole file **before** it selects profiles, and
`production-release.sh` passes that overlay to every command it runs. So with
the variable unset, `production-release.sh preflight` aborts on its first
compose call, before anything is built. Set it in
`/opt/mastersuite/apps/web/.env.production` first:

```
GRAFANA_ADMIN_PASSWORD=<a generated password>
```

This is a fresh requirement introduced by this PR; it did not exist at
`1f98183b`.

### 1 — Blank screen after lead create/edit · UNRESOLVED

Not reproduced here, so not diagnosed. Both journeys were driven again on
10 November at 375x812 against a seeded database, with the network and the
console recorded:

- **Create a lead and save** — 1 `POST /api/v1/leads`, destination rendered,
  `h1` showing the lead's name, no client error.
- **Edit details → change tags → save** — tags persisted and shown, page
  usable, no client error.

#### What was eliminated, and how

| Hypothesis                                    | Verdict                               | How                                                                                                                                                                                                                                                                                                                       |
| --------------------------------------------- | ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The write fails                               | **Eliminated**                        | The lead and the tags are in the database afterwards                                                                                                                                                                                                                                                                      |
| The service worker swallows the refresh       | **Eliminated**                        | `public/sw.js` answers only `navigate`-mode requests; an RSC payload is not one                                                                                                                                                                                                                                           |
| A missing page-level error boundary           | **Eliminated**                        | `app/error.tsx` exists and renders a panel                                                                                                                                                                                                                                                                                |
| **No `global-error.tsx` leaves a blank page** | **ELIMINATED — by experiment**        | A client error was thrown from inside the root layout, above `app/error.tsx`. Next 16.4.2 rendered its own default: "This page couldn't load — Reload to try again, or go back", with working Reload and Back buttons. **Not blank.** This was listed as a live hypothesis in the 9 November report and is now disproven. |
| `router.push()` racing `router.refresh()`     | **Real, measured, fixed** — see below |                                                                                                                                                                                                                                                                                                                           |
| A failed RSC fetch in the WebView             | **Still open**                        | Needs the device                                                                                                                                                                                                                                                                                                          |

#### The one thing that was measured

Creating a lead fetched the destination **twice, overlapping**:

| Request                                     | started | took   |
| ------------------------------------------- | ------- | ------ |
| `push()` → RSC fetch of the new lead page   | 52919ms | 1848ms |
| `refresh()` → RSC fetch of the **same URL** | 54260ms | 535ms  |

The second began 507ms before the first returned. `next.config.ts` already
states that the refresh is unnecessary — "this codebase navigates after a
mutation with `router.push` and relies on the dynamic staleTime of 0 to
re-render the destination". It was removed from the five record forms that do
exactly that. Afterwards: **one** fetch, 360ms, **one** POST, destination
rendered, and both newly created leads still listed after navigating back.

An aborted RSC fetch was separately observed on the Teams page
(`net::ERR_ABORTED` on a `router.refresh()` payload), where it cost a stale
list and nothing worse.

**This is not a claim that the race caused the blank screen.** It is a measured
defect on the reported journey, fixed on its own merits. Two overlapping
requests are free on localhost and are not free on a phone, where the first
takes seconds — but the symptom was never reproduced here, so the link is
unproven and is not recorded as proven.

No error boundary and no forced reload was added. Nothing was changed to make
the symptom invisible.

#### The remaining device checks

Four steps, on the affected phone, after the deploy:

1. Open **Safari** on the phone — not the app — to `https://one.youhan.in` and

Those four answers settle it. Until they come back it stays UNRESOLVED.

### 2 — Employee selection returns "0 items" · IMPLEMENTED, NOT DEPLOYED

**Root cause.** The control was `<select multiple>`. iOS renders that as a
single-line control that opens the one-column picker wheel, and that wheel
cannot express more than one choice, so every tap replaced the last and the
field stayed at "0 items" however many names were tapped. No amount of CSS
reaches it: the control is drawn by the system.

**Fix.** A checkbox group in `WorkspaceRecordForm` with 44px touch targets.
`FormData.getAll` already collected repeated names, so the submit path is
unchanged. The component builds the multi-choice field on 19 screens.

**Evidence.** In a browser at 375×812 against a seeded database: two employees
ticked, assigned, both rows present as `ACTIVE`/`PRIMARY` in
`HrEmployeeLocationAssignment`.

### 2b — The same defect on two further screens · IMPLEMENTED, NOT DEPLOYED

Found by asking the question the first fix should have asked: _where else?_
Two screens built their own multi-select rather than using the shared component,
and both were broken on a phone in exactly the same way:

- **Sales → Automatic assignment** — the "People" and "Only leads from these
  sources" pickers (`RulesPanel.tsx`). A rule could never be given more than one
  person on a phone, which silently changes who leads are handed to.
- **Administration → Teams** — the "Members" picker (`TeamsPanel.tsx`). A team
  could never be given more than one member on a phone, and TEAM data scope
  binds to that membership.

Both are now checkbox groups using the same classes. `getAll` was already used
on both submit paths, so neither server contract changed.

**Evidence from the running application**, at 375x812 and driven by mouse: on
Administration -> Teams, two members ticked and the team created comes back
holding both. Each row measures exactly 44px tall and the page does not scroll
sideways. On Sales -> Automatic assignment both groups render, no
`select[multiple]` remains, and an empty source list says so instead of
offering a dead control.

**Evidence.** `tests/unit/no-multiple-select.spec.ts` — new. It walks `src` and
fails on any `<select multiple>`, comments stripped. Confirmed to fail on the old
markup by restoring `TeamsPanel.tsx` and re-running. This is the regression test
for the whole class, not for one screen, because the defect is invisible to
anyone developing on a desktop.

### 3 — Test-like role options · IMPLEMENTED at source, NOT DEPLOYED

**Root cause.** Three Playwright specs clone roles and create accounts **inside
the shared demo workspace**, tagging what they create with their own
`Date.now()` rather than the run marker. `globalTeardown` deletes tenants whose
slug ends with `RUN_TAG`, so that workspace survives every run and its rows
accumulate, one set at a time: "Journey Rep …", "Scope probe …", "Daily
Workflow …".

**Fix.** The three specs tag with `RUN_TAG`; teardown also deletes roles and
work locations carrying it. Matched on the marker, never on "looks like a test".

**The rows already there are a separate problem.** The fix stops new ones. If
the suite has ever been pointed at a customer workspace, what is there are
grantable roles in a workspace somebody uses — a role boundary nobody chose.

There is now a way to see exactly what they are, without deleting anything:

```
node scripts/e2e-leak-inventory.mjs --slug <workspace-slug>
```

Read-only, with no `--apply`. It matches on the **generator** — the literal
template each spec used, with the run tag written as the eight lowercase
base-36 characters `Date.now().toString(36)` produces, anchored at both ends —
and never on "looks like a test". Proven on a seeded workspace: with
`journey_rep_mu8vfn6x` planted beside the decoys `journey_rep_dubai` and
`Seller 3`, it reported exactly one row and ignored both.

The slug is whatever `E2E_DEMO_SLUG` held when the suite ran, which is in that
environment's configuration. Deletion stays manual and by id: a role still
granted to somebody needs that grant moved first, and no script should decide
that.

**That `prisma.role.deleteMany` in the teardown carries no `tenantId`**, so it
matches across every workspace in the database it is pointed at. That is
intended for a disposable test database and is guarded by the isolation gate,
but it is worth knowing before anyone points the suite anywhere else.

### 4 — Ineligible reporting-manager options · IMPLEMENTED, NOT DEPLOYED

**Root cause.** The query filtered the employee record (`deletedAt`,
`employmentStatus`) and never the login behind it, and `setManager` accepted any
id the form sent. So "Deleted account – DEL-001" was offered and accepted.

This is worse than it looks: a manager who cannot sign in still approves leave
and payslips on paper only. A request routed to a suspended account waits with
nobody able to act on it.

**Fix.** The list requires `membership.status === 'ACTIVE'`; `setManager` and the
HR employee PATCH both refuse a non-active membership, so the rule holds for a
request that never came from the form. Reporting lines already recorded are left
exactly as they are — no historical record was rewritten.

**Evidence.** `tests/hr/manager-eligibility.spec.ts` — 3 cases. Both refusal
cases fail when the new check is removed, which was run to confirm it.

### 5a — Missing department / designation options · IMPLEMENTED, NOT DEPLOYED

**Root cause.** `Designation` had a complete API — list, create, update,
delete — and **no screen anywhere in the application**. No workspace could ever
configure one, so the field on **Add user** could only read "Not set".

**Fix.** Designations sit beside departments on the existing page, which becomes
**Departments & designations**. Where a list is genuinely empty the field says
"None configured yet" with a link to the setup page, instead of a dropdown
holding nothing.

**Evidence.** The focused HR journey creates a department through the UI and
asserts it appears — see section 3.

### 5b — Missing branch options · FIXED, AWAITING DEPLOYMENT

`Branch` rows could be created only by the demo seed: no API, no screen. Now a
resource like departments, with a screen at **People → Branches**.

The field on Add user was the smaller half. **BRANCH** is a record scope the
role editor offers beside ORGANIZATION and TEAM, and it binds to this set — so
in a workspace with no branches, a role granted it saw nothing, with no error
and no warning.

**No migration.** The model, its tenant scope and its indexes already existed;
only the way in was missing.

Evidence: `tests/hr/branches.spec.ts`, 5 cases green — create with the code
upper-cased, list, edit, a **409** while somebody is still posted there, and
archive leaving the list. In the running application, a branch created through
the new endpoint appeared in Add user's Branch dropdown on the next load.

### 6 — Missing sub-source options · IMPLEMENTED, NOT DEPLOYED

The control was correct — disabled because the chosen source has no
sub-sources — but a disabled "—" reads as broken. It now says which it is: "No
sub-sources configured for this source." or "Choose a source first."

### 7 — Lead validation inconsistencies · UNRESOLVED (a decision, not a defect)

Every rule is written down in [LEAD-VALIDATION.md](LEAD-VALIDATION.md), each
confirmed by calling the running API. The short version:

| Sent                             | Answer                                            |
| -------------------------------- | ------------------------------------------------- |
| `fullName` only                  | 200 — valid                                       |
| `fullName: ''`                   | 422                                               |
| `email: 'not-an-email'`          | 422 — email **is** format-checked                 |
| `phone: 'abcdefg'`               | **200**, stored verbatim, `phoneNormalized: null` |
| a second lead with the same name | 200 — a name alone is never a duplicate           |

Two findings. **The inconsistency is real and it is phone against email**: junk
normalises to null, so that lead matches neither phone-based duplicate rule,
cannot be dialled and will not be found by a number search — while looking
complete on screen.

**And the gap is narrower than "no validation":** only _custom_ fields can be
marked required. A workspace cannot require the built-in phone at all, and a
custom "Phone" field would be a second field invisible to duplicate detection,
the dialler and search.

Nothing was made mandatory and no format check was added. Both are decisions:
requiring both a phone and an email breaks import, and a phone format check
would start refusing numbers existing imports contain. The document separates
the three parts — which fields, at creation or at a stage gate, and whether API
keys and intake are exempt — so they can be answered one at a time.
