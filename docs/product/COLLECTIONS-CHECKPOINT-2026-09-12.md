## 1. Step 1 — the obligation model, inspected before anything was built

The "agreed agency fee due" is **`Booking.agencyFee`** — `Decimal(18,2)`, nullable, in `Booking.currency`. It already existed and was already load-bearing: the `PERCENT_OF_AGENCY_FEE` slab basis refuses to accrue commission when it is null (`commissions.ts:38`). So the amount and currency due _are_ representable, and no new field was needed for eligibility.

**The one gap, named rather than papered over:** there is no route that sets or amends `agencyFee` after a booking is created. A confirmed booking created without one cannot become eligible — by your rule, correctly — and today the only way to record the fee is at `POST /api/v1/bookings`. Amending the fee later changes the commission base for `PERCENT_OF_AGENCY_FEE` slabs, i.e. it _is_ a change to the commission agreement. **Not implemented; needs your decision:** may a finance role record or correct the agreed agency fee on a confirmed booking, and does doing so re-run accrual? The legacy audit (§5) lists every confirmed booking with no fee so the size of this is known before you answer.

**Lock order, stated once:** `Booking` (FOR UPDATE) → `AgencyFeeReceipt` (FOR UPDATE, decisions only) → `Commission` / `Payout`. Recording, reversing, verifying, collecting a commission, building, approving and paying a payout all take the booking row first. A reversal being verified and a payout being approved therefore cannot interleave; whichever is second sees the other's result and acts on it.

## 2.2 Usability — stated plainly: API-only

There is **no collections screen**. A finance user can record, verify, reject and reverse receipts only through `/api/v1/collections/receipts`, `…/decide` and `…/reverse` with a signed-in session or an API key holding the `collections` permissions. The artifact-level test (`tests/e2e/collections-api.spec.ts`) proves those calls work in the built image for four real signed-in people; it does not make the workflow usable by a finance clerk who has no API client. **A screen is remaining work (§9)**, and nothing in this checkpoint should be read as client-usable collections.

## 4. Two things I got wrong on the way, recorded

1. **I misdiagnosed a cleanup failure as a foreign-key design fault.** Three test workspaces were left behind because `payouts.spec`'s `afterAll` threw at `booking.deleteMany` (the receipt FK, RESTRICT, correctly refusing) _before_ reaching `fixture.cleanup()`. I wrote a migration switching the FKs to `NO ACTION` on the theory that RESTRICT breaks tenant cascade — then tested the theory by deleting one leftover tenant, which **succeeded**. The theory was wrong; the migration was deleted before commit; the fix is the cleanup order in two specs. Evidence: `receipt-fk-restrict-repro.log` says "deleted (unexpected)". The five leftover test workspaces were removed from the validation database.
2. **Payout tests interfered with each other** because a run gathers every collected commission a payee has and refuses a second run while one is outstanding. Each payout test now uses its own payee. That is the product working as designed, not a defect.

## 5. Legacy data — read-only audit, nothing grandfathered

`scripts/rc-collections-legacy-audit.mjs` lists, per workspace: bookings carrying `collectedAt` with no verified receipt; commissions `COLLECTED`/`PAID` whose booking is not covered; unpaid payouts containing them; confirmed bookings with no agreed fee. It changes nothing.

**What happens to those rows under the new code, exactly:** a legacy-`COLLECTED` commission keeps its status — the audit does not regress it and neither does any migration — but every payout gate now refuses to build, approve or pay a run containing it until verified receipts cover the fee (`not_covered:short` or `not_covered:agency_fee_unset`). So legacy status is inert rather than promoted. Finance decides each row: record the receipt properly, or withdraw the status.

On the validation database: 1 booking with `collectedAt`, 0 uncovered commissions, 0 blocked payouts, 0 fee-less confirmed bookings (`collections-legacy-audit.log`). **That says nothing about production**; the same script against production is in the operator evidence file.
