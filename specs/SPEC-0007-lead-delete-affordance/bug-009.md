# BUG-009 — Task deletion is granted, filtered for, and unreachable

| Field | Value |
|---|---|
| Bug ID | `BUG-009` |
| Title | Task deletion is granted, filtered for, and unreachable |
| Risk | `R3` — a new `/api/v1` route |
| Severity | Medium |
| Reported by | Bounded functionality audit, 2026-09-09 |
| Date | 2026-09-09 |
| Status | `FIXING` |

## Observed behaviour

`DELETE /api/v1/tasks/[id]` answers **`405 Method Not Allowed`**. No task
surface offers a delete.

## Expected behaviour

A task can be deleted by someone holding `tasks:DELETE`. Sourced from three
places that already exist:

- `tasks:DELETE` is in the permission catalogue and is **granted at
  `ORGANIZATION` scope to Company Administrator in the production database**;
- `Task.deletedAt` exists in the schema;
- every task read path already filters on it — `sales/tasks/page.tsx` and the
  follow-up queues both pass `deletedAt: null`.

Three parts of the product were built for a delete that was never wired.

## Reproduction

Disposable stack on `master-suite/web:c879c6c7f7e8`, as a workspace
administrator: create a task, then `DELETE /api/v1/tasks/<id>` → `405`.

## Affected requirement or specification

- [x] **No requirement covers this.** Closed by `SPEC-0007` `FR-008` to
      `FR-010`.

## Root cause

The handler was never written. `app/api/v1/tasks/[id]/route.ts` exports `GET`
and `PATCH` only, so Next answers `405`. Cancelling (`status: 'CANCELLED'`) was
the only way to get a task off the board, and it is a different thing — it
keeps the task visible as a decision someone took.

## Security impact

None. The new route is gated on `tasks:DELETE` via the API kernel, tenant-scoped
like every other handler in the file, and adds no bypass. Gating on
`tasks:DELETE` rather than the `leads:EDIT` the rest of the file uses follows
what every other delete route in the API does — accounts, contacts, campaigns,
events, listings, projects, visits, documents and leads all gate on their own
module's `DELETE` — so no authorization model is invented.

## Data impact

Soft delete: `deletedAt` is stamped, the row stays, and the lists already
exclude it. Nothing existing needs repair.

## Regression test

Covered by the bounded matrix (`TC-014`). A `405` before, `200` after, with the
row soft-deleted.

## Fix scope

A `DELETE` export in `app/api/v1/tasks/[id]/route.ts`, and a Delete control in
`TaskRowActions` gated on `can(ctx, 'tasks', 'DELETE')`.

**Not changed:** the `PATCH` handler's `leads:EDIT` gate, the cancel/complete
lifecycle, or the permission catalogue.

## Observation carried out, not fixed here

The whole task API is gated on the `leads` module (`GET`/`POST`/`PATCH` all
declare `module: 'leads'`), so the rest of the `tasks:*` permission set is
decorative. Changing that is an authorization-model change and belongs in its
own record.
