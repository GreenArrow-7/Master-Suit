## Observed behaviour

Reported as not established: whether an authorized user can attach a document
to a lead.

## Reproduction

**No defect reproduced.** Disposable stack, image `master-suite/web:c879c6c7f7e8`,
with the real ClamAV and a MinIO of its own.

| Case | Result |
|---|---|
| Authorized upload (`leads:EDIT`), through the Documents tab in a browser | `200`, stored, listed |
| Metadata row | `Document` row with tenant, lead, mime, size, `scanState CLEAN` |
| Storage key | `documents/t-<tenantId>/lead-<leadId>/<ulid>-<sanitised name>` |
| Download | `200`, bytes match, `Content-Disposition: attachment`, `X-Content-Type-Options: nosniff` |
| Upload without `leads:EDIT` | `403` |
| Upload against another tenant's lead | `404` |
| Filename `../../../../etc/passwd` | stored key `.._.._.._.._etc_passwd`; the same sanitiser runs again on download |
| 30 MB file | `413`, "Files must be under 25 MB." |
| EICAR test file | `422`, **not stored**, the attempt recorded with `scanState INFECTED` |
| Delete with `documents:DELETE` | `200`, soft-deleted |
| Delete without it | `403` |

The architecture already existed and there is exactly one of it: the `Document`
model with per-record foreign keys, `POST/GET/DELETE /api/v1/documents`,
`/api/v1/documents/[id]/download`, `lib/storage.ts`, `lib/antivirus.ts`, and
the Documents tab on the lead. No second attachment architecture was created.

## Why it looked missing

**Production holds zero `Document` rows** — the feature has never been used
there, which is not the same as broken. The control lives on the lead detail
page's Documents tab rather than on the lead's main view.

## Findings carried out, neither a defect nor fixed here

- The stored display `name` keeps the raw client filename. It is escaped by
  React on render and sanitised again in `Content-Disposition`, so it is
  cosmetic — recorded rather than changed.
- There is no MIME allowlist; any type may be uploaded. `attachment` plus
  `nosniff` on download is what makes that safe, and both are present.
- Production upload depends on `infra-clamav-1`. If that container is
  unhealthy every upload answers `422` "the malware scanner was unavailable" —
  correct behaviour, and worth an alert. It is healthy today.

## Regression test

`REG-002`, `tests/e2e/crm-lifecycle.spec.ts` — "a document uploads to the lead,
lists, and downloads". It uploads through the real control, asserts the file
lists, then pulls the bytes back through the authorised download route and
compares them.

**Status:** `CANNOT_REPRODUCE` — no defect. Coverage added so the absence stays
provable.
