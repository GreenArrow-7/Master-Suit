# BUG-008 — The platform console's redirect body carries the control-plane page

| Field | Value |
|---|---|
| Bug ID | `BUG-008` |
| Title | The platform console's redirect body carries the control-plane page |
| Risk | `R4` — the fix changes where authorization is enforced for eleven pages |
| Severity | High if reached; latent — see Reproduction |
| Reported by | Found while verifying `BUG-007`'s denial path, 2026-09-09 |
| Date | 2026-09-09 |
| Status | `REPRODUCED` — **not fixed; stopped at the R4 gate** |

## Observed behaviour

`GET /platform` answers `307` and a `Location` header, and **also returns a
response body**. In the disposable stack that body is the fully rendered
platform overview: every workspace name, the platform owner's address,
platform-wide user and employee counts, locked-account and sign-in-failure
counts, "privileged without MFA", and the recent platform security ledger
(`LOGIN`, `LOGIN FAILED`, `MFA ENROLLED`, with timestamps).

It is returned to an **unauthenticated** caller, and to any signed-in workspace
user. A browser follows the redirect and displays none of it. `curl` reads it.

## Expected behaviour

A caller refused the control plane receives nothing from it. Sourced from
`lib/auth/platform.ts` and `lib/auth/platform-policy.ts`: `OWNER` runs the
platform console, and `USER` "is deliberately not privileged here".

## Reproduction

Disposable stack, web container `master-suite/web:c879c6c7f7e8` — the image
production runs.

```
curl -s -o body.html -w '%{http_code}' http://<qa-web>/platform     # 307, ~31 KB body
grep -c 'Recent platform activity\|Manath Homes' body.html          # > 0
```

Reproduced with no cookie at all, with a company administrator's session, and
with an ordinary sales user's session. **It is not caused by the `BUG-007`
denial-UX change**: it reproduces identically on the unmodified production
image, whose branch redirects to `/login`.

**Against production it did not reproduce: 8 of 8 unauthenticated probes
returned a constant 23,735-byte shell with none of the strings above.** The
platform page loses the render race there and never serialises. That makes this
**latent and timing-dependent, not actively bleeding** — and timing is not a
control. Data volume, cache warmth and load all move it.

## Affected requirement or specification

- [x] **No requirement covers this.** Nothing states that a refused caller must
      receive no body, and the architecture assumed a layout guard was
      sufficient. It is not: in the App Router a layout cannot prevent the page
      beneath it from rendering, and neither `redirect()` nor `forbidden()`
      changes that.

## Root cause

`app/(platform)/platform/layout.tsx` was the **only** gate for the whole
console. Ten of the eleven pages under it assert nothing of their own — only
`platform/audit/page.tsx` does. The layout's refusal sets the response status
and location, but the sibling page has already been invoked and its output is
serialised into the flight payload of that same response.

Every one of those ten pages queries control-plane data.

## Security impact

Unauthenticated disclosure of control-plane metadata: customer workspace names,
the platform owner's address, platform-wide counts, and a security-event ledger
that names authentication outcomes. No credentials, no session tokens, no
tenant record contents. Registered in `docs/security/SECURITY_OBSERVATIONS.md`
with an exploitability status; no exploit path beyond the single GET above is
published here.

## Data impact

None written. Read exposure only.

## Regression test

To be written with the fix, as a request-level assertion — the body of the
refusal, not the rendered screen, because a browser never shows it. It must
fail against the current code, which it does by construction.

## Fix scope — proposed, NOT applied

Move the assertion to where the data is read: a shared guard invoked first in
each of the eleven platform pages, so a page that is not permitted performs no
query and produces no output. The layout keeps its gate for navigation.

Deliberately **not** attempted here:

- widening the layout's role — it structurally cannot do this job;
- a `middleware.ts` — the repository has none, and introducing one puts new
  code in front of every request in the product for a defect in one segment;
- leaving it to `forbidden()` — measured, and it has the same property.

## Why this is not implemented in this change

`docs/RISK_CLASSIFICATION.md` puts a change to where authorization is enforced
at `R4`, and `docs/sdd/BUG_WORKFLOW.md` puts any bug with a security dimension
at `R4` from the report onward. `R4` requires a human to accept the plan before
implementation, mandatory Application Security review, and two reviewers.
Production shows the defect is latent rather than active, so the correct action
is the gate, not a rushed eleven-file authorization change inside a
functionality fix.
