# BUG-006 — An administrator cannot delete leads

| Field | Value |
|---|---|
| Bug ID | `BUG-006` |
| Title | An administrator cannot delete leads |
| Risk | `R2` — the fix adds a bulk action to an existing grid over an existing endpoint |
| Severity | High — a routine administrative operation is unreachable in production |
| Reported by | Production user report, relayed 2026-09-09 |
| Date | 2026-09-09 |
| Status | `FIXING` |

## Observed behaviour

"An Administrator cannot delete Leads." Reported against
`https://one.youhan.in`, workspace `nityaraai01`.

## Expected behaviour

An administrator holding `leads:DELETE` can delete leads. Sourced from four
artefacts that already exist in the product, not from a new product decision:

- the `leads:DELETE` permission in `lib/security/rbac.ts`;
- the `Company Administrator` role's `ORGANIZATION`-scoped grant of it
  (confirmed in the production database, read-only);
- `DELETE /api/v1/leads/[id]`, which declares `action: 'DELETE'`;
- `deleteLead` in `services/leads/updateLead.ts`, and a Delete control already
  present on the lead **detail** page.

## Reproduction

Reproduced against a disposable stack, never against production.

**Environment.** A throwaway compose stack (`msqa`) on the same host: its own
PostgreSQL 16 (`leadflow_demo`), Redis and Mailpit, and the web container
running **`master-suite/web:c879c6c7f7e8` — bit-for-bit the image production is
running** (`org.opencontainers.image.revision`
`c879c6c7f7e8e45e90387a3f764599ba4667dfdc`). Schema built by
`prisma migrate deploy` from the same 66 migrations, then the demo seed. The
disposable database was compared against production before use: identical
migration set, identical RLS policies and `relrowsecurity`/`relforcerowsecurity`
flags on all 202 tables, identical `master_saas_app` grants. The application
connects as `master_saas_app` (`NOSUPERUSER`, `NOBYPASSRLS`) in both.

**Steps.** Sign in as the seeded workspace administrator (`org_admin`,
holds `leads:DELETE`), open `/manath-homes/sales/leads`, tick a lead's
selection checkbox.

**Actual.** The bulk bar appears offering exactly `Assign`, `Change stage`,
`Add task`, `Clear`. There is no delete. Driven in a real browser against the
production image, the bulk bar's buttons are:

```text
Assign | Change stage | Add task | Clear
```

Searching the shipped source confirms it: the only `method: 'DELETE'` against
`/api/v1/leads/` in the whole application is on the lead **detail** page,
behind a `More ▾` dropdown.

**Corroborating production evidence (read-only).** The web container's retained
request log covers 2026-09-06 08:01 → 2026-09-08 15:55, 194 kernel-logged
requests. **Not one is a `DELETE`.** The failing operation never reached the
server, in either direction — consistent with there being nothing to press.

## Expected versus actual

| | Expected | Actual |
|---|---|---|
| Leads list, administrator | a delete action for the selection | none exists |
| Lead detail, administrator | a delete action | present, behind `More ▾` |
| `DELETE /api/v1/leads/[id]` | `200`, soft-deletes | `200`, soft-deletes — **already correct** |

## Affected requirement or specification

- [x] **No requirement covers this.** The list's bulk actions were never
      specified against the permission set they are meant to expose, which is
      how `leads:DELETE` came to be granted, enforced and unreachable at the
      same time. Closed by `SPEC-0007` `FR-001`–`FR-004`.

## Root cause

**A missing user-interface affordance, not a defect below it.**

`LeadGrid` renders one bulk-bar button per capability it is told about, and it
was never told about `leads:DELETE`: `page.tsx` passed `canAssign` and
`canEdit` and no `canDelete`, and the grid had no delete handler. The detail
page passes `canDelete` and does have one — which is why deletion existed at
all, one record at a time, behind a menu.

Every layer below the screen was verified working on the deployed image, so
that the fix is not aimed at a symptom:

| Layer | Result |
|---|---|
| Permission grant | `leads:DELETE`, `ORGANIZATION`, granted to `company_admin` in production |
| API kernel authorization | asserts `leads:DELETE` before the handler |
| Route | `DELETE /api/v1/leads/[id]` implemented, `200 {"ok":true}` |
| Service | soft delete inside `withTx(ctx.tenantId, …)`, after `assertRecordVisible(…, 'DELETE')` |
| RLS | policies present and identical to production; `NOBYPASSRLS` role |
| Tenant isolation | cross-tenant delete answers `404`, row untouched |
| Related records | a lead carrying activities deletes successfully |

**Callers checked.** `deleteLead` has exactly two callers: the `DELETE` route
and `EntityDelete` (`components/sales/EntityDelete.tsx`) via the same endpoint
family. Neither is changed. The fix is in the one place that was missing a
control, and it re-uses the endpoint both existing callers use.

## Security impact

None. No authorization, visibility, tenant-context, RLS or session code is
touched. The new control renders on `can(ctx, 'leads', 'DELETE')` — the same
permission the API kernel asserts independently on every request — so a client
that renders the button anyway gains nothing. Negative cases were run
explicitly:

- a user without `leads:DELETE` → `403 Your role does not allow delete on leads.`
- an administrator deleting another tenant's lead → `404`, `deletedAt` still null.

## Data impact

None. Deletion is a soft delete (`deletedAt`); history, activities, tasks and
documents are retained. No existing data needs repair.

It has to be asserted on the list rather than against the endpoint: the
endpoint passed the whole time.

## Fix scope

`LeadGrid.tsx` gains a `canDelete` prop, a `deleteSelected` handler over the
existing endpoint, and a bulk-bar button; `leads/page.tsx` passes the
permission it already computes on the detail page. One word of the shared
bulk-failure message changes from "updated" to "completed", because the message
is shared with actions that are not updates.

**Not changed:** the endpoint, the service, the permission model, the soft- vs
hard-delete contract, the detail page's control, or anything under
`lib/security/` or `lib/auth/`.
