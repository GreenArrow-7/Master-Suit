## Observed behaviour

"Users/Administrators are unable to create a Workspace." No screen, account,
error text or timestamp was supplied with the report.

## Expected behaviour

A **Platform Owner** provisions workspaces through
`/platform/workspaces/new`. A workspace administrator does not: workspace
creation is a control-plane operation behind `requirePlatformOwner`, and every
entry point to it lives inside the platform console. Sourced from
`lib/auth/platform.ts`, `app/(platform)/platform/layout.tsx` and
`docs/AUTHENTICATION-DESIGN.md`.

## Reproduction

**Reproduction failed.** Recorded here in full, because a failed reproduction
is a finding.

Same disposable stack as `BUG-006`, running the exact production image
`master-suite/web:c879c6c7f7e8`, on a database whose migrations, RLS policies
and role grants were compared field-by-field against production and found
identical.

1. **API path.** Authenticated as the Platform Owner (password, then TOTP
   enrolment, then a `FULL` session) and `POST /api/v1/platform/workspaces`
   with a valid body → **`201 Created` in 0.52 s.** The whole
   `withPlatformTx` transaction — tenant, settings, subscription, module
   entitlements, usage rows, 246 permissions, the `company_admin` role and its
   grants, the workspace user, the platform identity, the membership, the
   membership role, the employee profile, lead stages, activity and task types,
   the pipeline and its stages, and the audit event — commits inside the
   default 5 s interactive-transaction budget.
2. **Wizard path.** Drove the five-step wizard in a real browser as the
   Platform Owner: filled Company details, Administrator, Subscription and
   Modules, reached Review, pressed Create workspace. One request:
   `POST /api/v1/platform/workspaces → 201`. No page error.
3. **Creator's membership** is correct: `isPrimaryAdmin`, `roleSnapshot`
   `company_admin`, a `MembershipRole` row, and the new tenant's own
   `company_admin` role holding all 246 permissions at `ORGANIZATION` scope.
4. **Tenant isolation after creation** holds: a lead belonging to the new
   workspace is invisible to, and undeletable by, the other workspace's
   administrator (`404`, row untouched).

**Production evidence, read-only.** `PlatformAuditEvent` shows exactly one
`WORKSPACE_CREATED`, at 2026-09-06 10:04:56 — **the wizard has worked in
production**. Since then the log records two Platform Owner sign-ins and ten
sign-ins by the workspace administrator (`platformRole` `USER`). The web
container log for 2026-09-06 → 2026-09-08 contains no
`workspace provisioning failed` and no 5xx.

Expected `201`; observed `201` everywhere it was exercised. The reported

## Root cause

**Not established.** Stating a cause here would be a guess, and the deployed
code answers `201`. What the investigation did establish is why the question
cannot be answered from the evidence that exists:

- `POST /api/v1/platform/workspaces` is the one mutation path that does **not**
  go through the API kernel `route()` helper, so it inherits none of its
  request logging. `problem()` logged only the unexpected-`500` branch. A
  `403`, a `409` or a `422` from this route was written **nowhere** — not to
  the application log, not to the audit trail. A user reporting "creation
  fails" therefore leaves no trace at all.
- The wizard renders a `422` as the bare words "Validation failed", because
  that response carries `errors.fieldErrors` and no `detail`, and the form
  read only `detail ?? title`. Five steps of typing, and no indication of
  which field on which step was rejected.

Two candidate explanations remain open, both consistent with everything
observed, and neither is claimed:

- **C1 — wrong actor.** The reporter is the workspace administrator
  (`contact.nityaraai@gmail.com`, `platformRole` `USER`), for whom workspace
  creation is correctly refused. Reaching `/platform` with a valid workspace
  session answers `307 → /login`
  (`app/(platform)/platform/layout.tsx` catches and redirects), which to a
  signed-in user reads as the application throwing them out rather than as
  "you do not have access here" — and would also explain "multiple application
  functions appear not to work". Ten of the twelve most recent sign-ins are
  this account.
- **C2 — a validation rejection.** The owner was rejected by `422` or `409`
  and shown "Validation failed" with no field named, or "That workspace slug is
  already in use."

**Evidence needed to close, which only the reporter or DevOps can supply:**
which account was signed in, what the screen said verbatim, and the date and
time. With `FR-005` deployed, the third of those is enough on its own.

## Security impact

None from this change. `FR-006` explicitly forbids logging field values, so the
new records cannot leak the administrator password the wizard submits.

## Data impact

None. No partial workspace was found in production: one `Tenant` row, one
`WORKSPACE_CREATED` event, and a complete role, membership and configuration
set behind it. `withPlatformTx` is a single interactive transaction, so a
failure part-way rolls the whole provisioning back.

## Regression test

None. There is no reproduced failure to regress against, and a test written
against a guessed cause proves nothing. The wizard path is already covered end
to end by `createWorkspaceViaWizard` in `apps/web/tests/e2e/helpers.ts`, used
by `crm-lifecycle.spec.ts` and others — which is further evidence that the
happy path works.

## Fix scope

Diagnosability only, and it is deliberately not called a fix for the symptom:

- `POST /api/v1/platform/workspaces` logs every rejection with request id,
  status and either the error code or the failing field **names**.
- The wizard names the failing fields on a `422`.

**Not changed:** the provisioning transaction, `requirePlatformOwner`, the
platform layout's redirect (candidate `C1` — unevidenced, and it is
authorization-adjacent, so it is not being changed on a hunch), or the wizard's
validation rules.
