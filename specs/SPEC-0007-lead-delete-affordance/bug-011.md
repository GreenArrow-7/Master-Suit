# BUG-011 — An administrator cannot delete a call

| Field | Value |
|---|---|
| Bug ID | `BUG-011` |
| Title | An administrator cannot delete a call |
| Risk | `R3` — a new `/api/v1` route; the permission, the column and the component all already existed |
| Severity | Medium |
| Reported by | Release owner, 2026-09-09 |
| Date | 2026-09-09 |
| Status | `FIXING` |

## Observed behaviour

Sales → Calls → a call's detail page offers no delete. `DELETE /api/v1/calls/[id]`
answers **`405`**.

## Expected behaviour

An administrator holding `calls:DELETE` can delete a call. Sourced from four
things already in the product:

- **`calls:DELETE` already exists** and is already enforced — `objections/[id]`
  and `sales-playbooks/[id]` both gate on it;
- the call detail page **already reads it**, as `canDeleteAudits`, to decide
  whether to show `AuditDelete`;
- **`Call.deletedAt` already exists**;
- every read path already filters it — the list page, the list API, and the
  transcript, analysis and recording-metadata sub-routes.

The authority, the column, the filters and the UI component were all present.
Only the endpoint and one control were missing. The same shape as `BUG-006`
(leads) and `BUG-009` (tasks).

## Root cause

`app/api/v1/calls/[id]/route.ts` exported `GET` and `PATCH` only, so Next
answered `405`, and no call surface rendered a delete.

## Delete semantics — soft, and not a retention event

`deletedAt` is stamped; the row stays. **The recording, its stored object, the
transcript, the AI analysis, the consent record and the call audits are all left
exactly as they are.**

Recording lifetime is owned by `lib/jobs/retention.ts`, which deletes by
`retainUntil`, removes the object *before* the row so audio is never abandoned
in the bucket, and skips provider-hosted media. Deleting the object here would
take that decision from the policy that owns it and destroy consent and audit
evidence the product keeps deliberately. **A call being removed from a workspace
is not a retention event.** This is option A of the three the brief listed, and
it is the repository's existing rule rather than a new one.

## A second gap, found while tracing and closed

`calls/[id]/recording/media` — the only path to the audio bytes — queried
`Recording` by `callId` alone. Every sibling route filters the parent call's
`deletedAt`; this one did not. Harmless while nothing could delete a call;
**the moment deletion exists, a deleted call's recording would still stream** to
anyone holding `calls:VIEW`, making the deletion cosmetic exactly where it
matters most. The route now resolves the call first.

## Security impact

None added. The new route is gated on `calls:DELETE` through the API kernel,
tenant-scoped, and adds no bypass. The media guard **removes** an exposure that
shipping deletion would otherwise have created.

## Verified

| Case | Before | After |
|---|---|---|
| `DELETE /api/v1/calls/{id}` as `org_admin` | **`405`** | `200`, `deletedAt` set, row retained |
| Delete control on the detail page, admin | **absent** | visible; arms, then "Delete call" / "Keep" |
| Delete control, `sales_rep` | absent | **absent** |
| API delete as `sales_rep` | — | `403` "Your role does not allow delete on calls." |
| API delete as `read_only` | — | `403` |
| Cross-tenant delete | — | `404`, other tenant's call untouched |
| Repeat delete | — | `404` |
| Deleted call in the list API | — | excluded (47 remaining) |
| Deleted call `GET /api/v1/calls/{id}` | — | `404` |
| Deleted call detail page | — | the project's not-found state, no stale content; a never-existing id behaves identically |
| Recording, consent, `retainUntil` after delete | — | **retained** |
| Recording media for a deleted call | proceeds past the call check | **`404`, refused at the call level** |

## Regression test

`REG-004`, `apps/web/tests/e2e/crm-lifecycle.spec.ts` — "an administrator
deletes a call from its detail page": creates a disposable call, arms and
confirms through the real control, asserts the redirect to the list, that the
call is gone from it, that `GET` answers `404`, and that a second delete is a
`404` rather than a second success.

## Fix scope

`DELETE` in `app/api/v1/calls/[id]/route.ts`; the parent-call guard in
`recording/media/route.ts`; `EntityDelete` on the detail page gated on
`can(ctx, 'calls', 'DELETE')`.

**Not changed:** the retention policy, storage handling, the permission
catalogue, RLS, or any other call route. **No list-row control was added** —
accounts, contacts and opportunities all keep destructive actions on the detail
page only, and the brief says not to add a second UI where that is the
convention.
